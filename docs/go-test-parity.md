# Go test parity checklist

Tracks every Python unit/system test function (≈127 unit tests across
`test/` and `test/unit/`, plus the systest suites) as one of:

- **ported** — the assertion was ported to a Go test (name the Go test).
- **Go-idiomatic** — replaced by a Go-native equivalent (e.g. `-race` tests
  replacing thread-interleaving tricks, `httptest` replacing `responses`).
- **dropped-with-reason** — Python-internals-only test with no Go
  equivalent; the reason is recorded.

Each task's builder updates its rows; Task 29 (final parity sweep) verifies
completeness. Table state is per migration commit.

Recorded deviation (user decision, Task 3 review; NEWS in plan Task 28):
the running-config dump is parsed-JSON-equal to Python's
`json.dump(..., sort_keys=True)` but **not byte-identical** — Go renders
floats like 60.0 as "60", 1e-05 as "0.00001", and 1e+20 as
"100000000000000000000" (Python: "60.0", "1e-05", "1e+20"), and emits
non-ASCII as raw UTF-8 where Python's `ensure_ascii=True` writes \uXXXX.
All parity assertions above compare parsed JSON, so none of them depend
on the byte-level difference.

## Task 4 — journal entry model, converters, JSON serialization

Source: `test/test_journalpump.py` seqnum tests; the serialization parity
has no Python unit test (Python's `json.dumps` is the oracle itself), so
the golden fixture is generated by actually running the Python pipeline
(`internal/journal/testdata/generate_golden.py` →
`serialization_golden.jsonl`).

| Python test | Status | Go counterpart |
|---|---|---|
| test_pump_reader_get_next_includes_seqnum | ported | `TestParseSeqnumFromCursor` (`i=1f4` → 500) + `TestSerializeGolden/typical` (full enrichment-to-wire path: `__SEQNUM` appended only when parsed, converter table, repr fallback, timestamp, extras, `json.dumps` bytes) |
| test_pump_reader_get_next_seqnum_missing_or_invalid (3 param cases) | ported | `TestParseSeqnumFromCursor` (no `i=`, empty `i=`, non-hex `i=`) + `TestSerializeGolden/invalid-utf8` (cursor without `i=`) |
| (no Python unit test — Python json.dumps/repr/datetime are the oracle) | Go-native | `TestSerializeGolden` byte-identical against Python-generated fixtures incl. invalid-UTF-8 repr strings (with CPython's quote selection: `b"don't\xff"` uses `"` as delimiter — `repr-quote` fixture), converter failures, UUID canonicalization, extras overwrite-in-place, `ensure_ascii` escapes, Python float repr (`60.0`/`1e-05`/`1e+20`), list values, timestamp overwrite-in-place |
| (Python int() quirks) | Go-native | `TestPythonIntString` + `TestConvertEntry` (whitespace, signs, base-16 `0x` prefix, underscores between digits, out-of-int64 → verbatim decimal) |
| (fuzz target) | Go-native | `FuzzParseSeqnumFromCursor` (seed corpus from the parity cursors + naive reference oracle; ~470k execs clean) |

Go-idiomatic note: `ProcessEntry` reprs every bytes value exactly like
Python's `isinstance(value, bytes)` branch; valid-UTF-8 bytes never reach
it because `convert_entry` already decoded them. Undecodable bytes that
reach `Serialize` directly are refused (Python raises
UnicodeDecodeError). Nested objects in `extra_field_values` are carried
as ordered `[]Field` (document order) and the serializer refuses
unordered `map[string]any`, so nested key order cannot silently change
on the wire; config decoding captures document order when the extras are
wired in plan Task 16.
